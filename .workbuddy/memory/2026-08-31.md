## Project 2 / Step 5 讲解：quant_pre_process 的契约价值

用户问 notebook `01_ptq_qdq_compiler_contract.ipynb` Step 5 前言里
「shape 已知 + 可融合结构已规整 → 先 quant_pre_process → 便于 graph matching」这一段怎么体现。

产出：`notebooks/project2_quant_compiler/step5_preprocess_contract_demo.py`（可复跑，5 个 Part，实测通过）。
跑法：`uv run python notebooks/project2_quant_compiler/step5_preprocess_contract_demo.py`

### 实测结论（本机 M1 + ORT 1.21 + onnx 1.17）

- `quant_pre_process()` 源码（`.venv/.../onnxruntime/quantization/shape_inference.py`）实际只做 3 件事：
  1. `SymbolicShapeInference.infer_shapes`（依赖 sympy）
  2. ORT **ORT_ENABLE_BASIC** 原生优化器（不是 ENABLE_ALL）
  3. `onnx.shape_inference.infer_shapes_path` 补 value_info，最后 `add_pre_process_metadata` 打 tag
     `onnx.quant.pre_process=onnxruntime.quant`
- 关键实测（不规则图 15 nodes vs 预处理后 4 nodes）：
  - 静态 `onnx.shape_inference` 遇到 `Shape→Gather→Unsqueeze→Concat→Reshape` 会断，`R` 退化成 `unk__0/unk__1`；
    符号推理能恢复成 `['batch','8']`。
  - ORT basic 优化器一轮：Transpose 对消除 + Identity 消除 + Constant×Constant 折叠 + MatMul+Add→Gemm。
  - quantize_static 后：raw 图 31 nodes / Q=7 DQ=9；预处理图 14 nodes / Q=4 DQ=7。
  - **per-channel 差异最关键**：raw 图把 bias `B` 当独立 per-tensor 张量量化（错）；
    预处理后 bias 变成 `B_quantized_scale`（长度 8 的 per-channel 向量），且实测
    `B_quantized_scale == X_scale * W_MM_scale`（误差 0.000e+00）—— bias scale 是推出来的，不是统计出来的。
  - 后端 optimizer 结果：raw → `QLinearMul + QLinearMatMul + QLinearAdd + QLinearMul`（4 个 int8 kernel，
    MatMul/Add 之间多一次 dequant→requant 往返）；预处理 → `QGemm + QLinearMul`（融合成功）。
  - 跳过预处理时 ORT 自己会 warn：`Please consider to run pre-processing before quantization.`

### 教学结论（复用口径）

- 「规整」= 6 条可机检条件：静态 shape / 单一定值(SSA-like) / 可融合结构已收敛成 canonical form /
  常量已折叠 / 无冗余算子 / 拓扑有序。**不是审美问题。**
- 「graph matching」的真实价值不是名字对得齐，而是：
  预处理图的 FP32 侧与 INT8 侧共享同一套中间 tensor 名，误差可逐层归因；
  未预处理图 INT8 侧会冒出 `MM`/`SCALE` 这类在 FP32 优化图里根本不存在的 tensor，误差归不了因。
- 数值误差差异在 toy 上很小（3.152 vs 3.103，输出量级 34.8），**不要拿它当卖点**，
  卖点是结构/kernel 选择，不是误差。

### 环境备忘

- `protoc` 本机可用（`/opt/homebrew/bin/protoc`，libprotoc 33.4）——
  `protoc --decode_raw < model.onnx` 是不依赖 onnx.proto 的通用检视手段，很好用。
- 构造 demo 图时 `Unsqueeze` 在 opset 13+ 需要 axes 作为**输入 tensor**，不能只给 attribute。

## 追问答疑：initializer 的角色 + quantize_static 的「自动识别」

产出：`notebooks/project2_quant_compiler/step5b_initializer_and_autodetect_demo.py`（4 个 Part，实测通过）。

### initializer 的四种角色（实测 tiny_token_mlp_w8a8_qdq.onnx：6 → 30 个）

不是只有 scale / zero_point，共四类：

1. **量化后的权重**（3 个）：`fc1.weight_quantized [512,256] int8`
2. **权重的 scale / zero_point**（6 个）：`fc1.weight_scale [512] fp32` + `fc1.weight_zero_point [512] int8`
3. **激活的 scale / zero_point**（12 个）：`input_scale []` 等，全部 0 维标量
4. **bias 的 int32 版本 + 它的 scale / zp**（9 个）：`fc1.bias_quantized [512] int32`

关键：`fc1.weight`（fp32）**被移除**而不是并存，拆成上面 1+2 三件。
scale 必须进 initializer 是因为 `QuantizeLinear` 把它当**图输入**用：
`input_QuantizeLinear inputs=['input','input_scale','input_zero_point']`。

### quantize_static 的「自动识别」= 查表 + 输入位置约定（硬编码）

- `onnxruntime/quantization/registry.py`：`QDQRegistry` 25 个 op、`QLinearOpsRegistry` 26 个 op。
  注意 `Add`/`Mul`/`Sigmoid`/`Softmax` **不在** QDQRegistry（只在 QLinearOpsRegistry）。
- `QDQGemm.quantize()` 逻辑：input[0]→activation、input[1]→weight、input[2]→bias，
  `default_axis = 0 if is_B_transposed(node) else 1`。
- 不在注册表的 op 走 `QDQOperatorBase` 回退：**无脑给所有 input/output 插 Q/DQ**（所以 Q/DQ 多 ≠ 快）。
- bias 若不是 initializer 会 warn：`Bias of Gemm node ... is not constant`。

### per-channel / per-tensor 的决定链（实测）

| 配置 | W_quantized | W_scale | X_scale |
|---|---|---|---|
| transB=1, per_channel=True | (8,4) | [8] → axis=0 | [] |
| transB=0, per_channel=True | (4,8) | [8] → axis=1 | [] |
| transB=1, per_channel=False | (8,4) | [] per-tensor | [] |

- activation 永远 per-tensor（`quantize_activation_tensor` 没有 axis 参数）
- weight 是否 per-channel 由 `per_channel=True` 决定
- axis 由 op 的 `default_axis` 给，而它依赖 **transB 这个 attribute** → 又回到 Step 5 的结论
- bias scale = input_scale × weight_scale × beta，实测误差 0.000e+00（推导，非统计）

### 重要更正：quantize_static 会自己兜底做 shape inference

`quantize.py` 里：`if not model_has_pre_process_metadata(model): logging.warning(...); model = load_model_with_shape_infer(...)`.
所以「跳过 quant_pre_process」不会导致没有 value_info —— 但兜底跑的是**静态**推理，
不是 `quant_pre_process` 里的**符号**推理。实测：

| | R 的 shape | nodes | Q/DQ |
|---|---|---|---|
| raw（ORT 兜底静态） | `['unk__0','unk__1']` | 31 | 7 / 9 |
| pre（符号推理） | `['batch','8']` | 14 | 4 / 7 |

- `QDQQuantizer._is_tensor_quantizable` 最后一档：tensor 既非 initializer 又不在 `value_infos`
  → 只打 `logging.warning("failed to infer the type of tensor ...")` 就返回 False，**静默跳过量化**。
  我这组 toy 图没触发（兜底补回来了），自定义 domain / 新算子才会命中。

## Check 1 解读：23 节点 → 11 节点的含义（用户误读纠正）

用户表：FP32 preprocessed 5 nodes / W8A8 raw QDQ 23 / W8A8 ORT optimized 11（3 QGemm, 2 Relu, 3 Q, 3 DQ）。

### 关键纠正
- "前端替换了 23 个算子"是错的：raw QDQ 23 = 原始 5 个 compute op（3 Gemm+2 Relu，原样未变）
  **+ 18 个 Q/DQ 节点**（quantizer INSERTED，不是 replaced）。compute op 仍是 float Gemm/Relu。
- "23→11 是回退"错了：是 **fusion**。ORT 把 `DQ→Gemm→Q` pattern 融合成单个 `QGemm`，
  删掉了 9 个 DQ + 3 个 Q 节点（12→3 DQ，6→3 Q）。
- **回退的正确判据**：stage2 里是否还有 `Gemm`（float compute fallback）。本例 stage2 op counts
  无 `Gemm`，3 个全变 `QGemm` → **无 compute fallback**，INT8 计算确实发生了（"quantized compute ops=3"）。
- 真正的小遗憾：**2 个 Relu 留在 float 域，成为 conversion boundary**。QGemm 输出 int8 → DQ(float)
  → Relu(float 计算) → Q(int8) → 下一个 QGemm。每个 Relu 造成一次 dequant→requant 往返
  （额外 rounding error + 内存 traffic）。理想情况是 Relu 融合进 QGemm（fused activation），
  那样 11 节点可降到 ~5（3 QGemm(fused)+1 input Q+1 output DQ），INT8 子图连续无切开。

### 证据（已 dump 确认）
- 优化图实际链：`Q(input) → QGemm → DQ → Relu → Q → QGemm → DQ → Relu → Q → QGemm → DQ(logits)`
- 3 QGemm 输出被 DequantizeLinear 消费 → 证实 QGemm 输出是 int8，Relu 在 float 域。
- 剩余 6 个 Q/DQ 的归属：input 量化(1 Q) + 2 个 Relu 各(1 DQ+1 Q) + 最终输出反量化(1 DQ)。

### 教学口径
"Q/DQ 越多不代表越快；理想态是内部连续 INT8 子图，边界 Q/DQ 尽量少。"
判回退看 stage2 op counts 里的 `Gemm`（compute fallback）；判 conversion boundary 看 `DQ→Relu→Q` 模式。
公司 NPU 同理：AGE partition log 里 MatMul/Gemm 是否落在 NPU subgraph，Relu 是否被融进 kernel。

## 追问答疑：Check1 的 backend optimizer 是不是 Core ML / AllSpark

### 结论
- Check1 的「optimized」= ORT 自己的进程内 graph optimizer（`SessionOptions().optimized_model_filepath` 落盘），
  **不是 Core ML / AllSpark**。落盘产物仍是 ONNX 格式（11 节点图，已 `onnx.load` 验证），不产生 .mlmodel / .ap。
- 用户抽象「前端产 QDQ + 后端优化」成立，但 Check1 的「后端」= ORT 自己；ORT 的 graph optimizer 与
  `quantize_static` 同进程同库，是 Step 5 里 `ORT_ENABLE_BASIC` 优化器的延伸。
- **真正的 Core ML / AllSpark 是独立转换链**，消费同一份 raw QDQ，但产物不同：
  - Core ML: `coremltools.convert(qdq)` → MIL optimizer → `.mlmodel`（ANE/CPU）
  - AllSpark: ONNX QDQ → AGE 图编译(≈ quant_pre_process) → HAUK/ACE 算子编译 → `.ap`（NPU）
    （图编译对硬件抽象只有 3 参数 `set_hardware_info(cluster_num, cluster_l2_size, global_l2_size)`）

### 关键实测（从 `tiny_token_mlp_w8a8_ort_optimized.onnx` dump）
- 11 节点链：`Q(input) → QGemm → DQ → Relu → Q → QGemm → DQ → Relu → Q → QGemm → DQ(logits)`
- **每个 Relu 两侧 scale 完全相同、zp 同为 0**：`/relu1/Relu_output_0_scale = 0.020729989`（DQ 侧与 Q 侧一致），zp=0
  → `DQ → Relu → Q` 是等距 identity 重量化。

## 追问答疑：对称量化 zp=0，ReLU 为何还是 Float 算子

### 结论（用户直觉正确）
- 对称 per-tensor zp=0 时，int8 网格上 `ReLU_int8(q) = max(q, 0)`，与「DQ→Relu(float)→Q」数学等价、零误差。
  已用真实 artifact 核实：Relu 两侧 s 同为 0.020729989、zp 同为 0。
- ORT 没把 Relu 融进 QGemm，是 **ORT QDQ fusion 规则在该路径未触发（融合保守）**，不是数学必须。
  → 印证 cell 26「DQ→Relu→Q 说明 INT8 子图被 float 切开」是现象真、原因为实现策略。
- **反例（check1_boundary_cost_demo.py）**：激活改非对称（zp=-128）→ Relu **被融合消除**，图从 11 节点缩到 5 节点
  （`Q → QGemm → QGemm → QGemm → DQ`），因为 QuantizeLinear 的饱和裁剪 + zero_point=下界 免费等价于 ReLU。
  实测延迟：非对称 ~0.0471 ms vs 对称 ~0.0753 ms（对称约慢 60%，多出 DQ/Q 往返 + 独立 Relu 内核）。

### 教学口径
「量化方案（对称/非对称）选择会直接改变图结构与 kernel 数量，进而影响延迟」——可测量差异，
讲面试素材时用「对称 vs 非对称 → Relu 是否融合」作现成证据。

## 新主题：NPU 厂商后端如何支持 Raw QDQ（Toy Compiler 演示）

用户视角切换成「NPU 厂商编译器开发者」：问是否必须支持 Raw QDQ + 要典型 op + Toy Compiler。

### 结论
- QDQ 是前端量化器（ORT/TensorRT/PyTorch PTQ/TF）与后端编译器之间的**事实标准量化 IR 契约**；
  厂商后端一般必须写 QDQ 前端 ingestion，否则接不进主流框架量化出的模型。
- 选 QDQ 而非 QLinear\* 的原因：QLinear\* 把 scale/zp 算术烤死在算子内，后端无优化空间；
  QDQ 把量化显式拆成 `DQ/op/Q`，留给编译器融合、重排、甚至 lowering 阶段重定量化参数。
- 厂商支持 QDQ = 三趟 pass：
  1. **融合**：识别 `DQ→op→Q` 坍缩成 int8 kernel（QGemm 等）；连续 op 间的 `Q(s)→DQ(s)` 身份重量化边可被融合。
  2. **量化参数传播 + requant 决策**：追踪每个 tensor 的 scale/zp；两不同 scale 的 int8 张量相遇（残差 Add）→ 内部 requant。
  3. **分区**：NPU-int8 子图（Gemm/Conv/Add…）vs CPU-float 边界（LayerNorm/Softmax 数值敏感）；
     QDQ 边界天然就是 NPU↔CPU 切分点。

### 产出文件
`notebooks/project2_quant_compiler/toy_qdq_compiler.py`（可复跑，`uv run python ...`）。
结构：RAW(24 nodes, 按 ORT 真实 raw QDQ：`DQ(s_in)→op→Q(s_out)`，op 间 `Q(s)→DQ(s)`) →
`compile()` 做 region 划分（连续 NPU_INT8 ops 融一核；CPU_FLOAT ops 打断）→ 3 kernels。
实测：24 nodes → **3 kernels**：
- NPU: `QGemm+Relu+QGemm+Relu+QAdd` enter_s=0.0349 exit_s=0.0016；
  **对称 Relu 前后 scale 不变=身份边 → 被融进 QGemm**（对比 ORT 保守地把它留成 float 边界）。
- Add 内部 requant: `0.004 & 0.0349 → 0.0016`（实测修正：初版 bug 取错 DQ，已改 `producer_of[input]` 直接拿 DQ scale）。
- CPU: `FloatKernel(LayerNorm)`, `FloatKernel(Softmax)`，前后 DQ/Q 为 int8↔float 转换边界（对应 AllSpark Fermat 向量核）。

### 对接 AllSpark 档案
- Cayley 吃 Gemm/Conv 经 `mmb_*`，`mmb_bias`/`mmb_deq` 说明 bias 加与反量化内联在矩阵单元
  ≈ 我们的 QGemm fused kernel（权重+偏置+反量化一次成型）。
- Fermat(SIMT) 吃向量 op ≈ 我们的 CPU/float 边界（LayerNorm/Softmax）。
- AGE 图编译的硬件抽象仅 `set_hardware_info(cluster_num, cluster_l2_size, global_l2_size)` ≈ 我们的 `partition()` pass。
- 切分点 = QDQ 边界这条结论，直接对应 AGE partition log 里 MatMul/Gemm 是否落 NPU subgraph。
